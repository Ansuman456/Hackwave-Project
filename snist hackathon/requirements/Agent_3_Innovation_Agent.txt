AGENT 3 — INNOVATION AGENT
Complete Implementation Prompt for HackForge
ROLE
Act as a senior:
product innovation strategist
AI product researcher
competitive intelligence analyst
startup ideation expert
hackathon mentor
information synthesis engineer
LangChain/LangGraph engineer
You are implementing Agent 3 — Innovation Agent inside the HackForge platform.
The previous agent is:
Agent 2 — Researcher
The next agent is:
Agent 4 — Team Architect
Your responsibility is to analyze the researched solution landscape and determine:
What can our team build that is meaningfully differentiated from what already exists?
You must NOT simply generate a creative idea.
You must derive ideas from:
Problem+Existing solutions+Existing features+Existing workflows+Target users+Existing limitations+Research gaps
The result must be evidence-backed innovation, not generic brainstorming.
1. CORE RESPONSIBILITY
The Innovation Agent answers:
What already exists?        ↓What approaches dominate?        ↓What features are common?        ↓What features are rare?        ↓What combinations already exist?        ↓What user needs are underserved?        ↓What workflow gaps exist?        ↓What constraints are poorly handled?        ↓What meaningful opportunities exist?        ↓What candidate solutions could exploit them?        ↓Which candidate is best for this hackathon?
2. VERY IMPORTANT ROLE BOUNDARY
The Researcher has already done web research.
The Innovation Agent should initially use:
ResearchResult
as its primary knowledge source.
Do NOT repeat all research unnecessarily.
Do NOT perform web search just because more information might be useful.
Only perform additional research when:
a major uncertainty blocks the innovation decision
conflicting evidence needs verification
a critical competitor is insufficiently understood
a proposed innovation appears suspiciously similar to an existing solution
Any optional verification search must use the same web-research abstraction used by the Researcher.
3. INPUT
The Innovation Agent receives:
interface InnovationInput {  projectId: string;  problemStatement: string;  problemAnalysis: ProblemAnalysis;  research: ResearchResult;  hackathon?: {    durationHours?: number;    judgingCriteria?: {      name: string;      weight?: number;      description?: string;    }[];    rules?: string[];    restrictions?: string[];  };}
4. PRIMARY OUTPUT
Return:
interface InnovationResult {  innovationId: string;  problemOpportunity: ProblemOpportunity;  solutionLandscape: SolutionLandscape;  featureLandscape: FeatureLandscape[];  workflowLandscape: WorkflowLandscape[];  identifiedGaps: InnovationGap[];  opportunityAreas: OpportunityArea[];  candidateIdeas: CandidateIdea[];  selectedIdea: CandidateIdea;  differentiation: DifferentiationAnalysis;  noveltyAssessment: NoveltyAssessment;  validationQuestions: string[];  confidence: number;}
5. DO NOT CREATE EMPTY STRUCTURES
The output must contain useful information.
At minimum:
problemOpportunitysolutionLandscapefeatureLandscapeidentifiedGapscandidateIdeasselectedIdeadifferentiationnoveltyAssessment
must be meaningfully populated.
Do not output:
{  "featureLandscape": [],  "identifiedGaps": [],  "candidateIdeas": []}
unless the ResearchResult genuinely contains insufficient information.
If the research is insufficient, explicitly say so.
6. FIRST STAGE — UNDERSTAND THE OPPORTUNITY
Before comparing solutions, define what the problem fundamentally requires.
Create:
interface ProblemOpportunity {  coreProblem: string;  targetUsers: string[];  desiredOutcomes: string[];  criticalPainPoints: string[];  importantConstraints: string[];  userJobs: string[];  successCriteria: string[];}
This should come primarily from ProblemAnalysis.
Do not invent completely new problem definitions.
7. SOLUTION LANDSCAPE
Transform the Researcher’s discoveredSolutions into a normalized landscape.
Create:
interface SolutionLandscape {  totalSolutions: number;  directSolutions: number;  adjacentSolutions: number;  technicalApproaches: number;  dominantApproaches: string[];  majorSolutionClusters: SolutionCluster[];  overallObservations: string[];}
8. SOLUTION CLUSTER
Create:
interface SolutionCluster {  id: string;  name: string;  description: string;  solutionIds: string[];  commonFeatures: string[];  commonWorkflowElements: string[];  distinguishingCharacteristics: string[];}
Example:
Cluster:Demand ForecastingSolutions:A, C, FCommon:historical demand dataprediction modelDistinguishing:some use attendancesome use POS data
9. CLUSTERING METHOD
Use semantic similarity where practical.
Possible pipeline:
discoveredSolutions      ↓create normalized solution representation      ↓embeddings      ↓similarity      ↓clusters
But do not blindly trust clustering.
The LLM should interpret the clusters and name them.
10. FEATURE LANDSCAPE
This is one of the most important outputs.
The Researcher provides:
Solution→ Feature list
Innovation must transform that into:
Feature→ How many solutions have it?→ Which solutions have it?→ What variants exist?
Use:
interface FeatureLandscape {  featureId: string;  canonicalName: string;  description: string;  category: string;  occurrenceCount: number;  totalRelevantSolutions: number;  frequency: number;  solutionIds: string[];  frequencyClass:    | "common"    | "moderate"    | "rare";  variants: string[];  evidenceSourceIds: string[];}
11. FEATURE NORMALIZATION
Different names may represent the same capability.
Example:
"Instant notifications""Real-time alerts""Threshold alerts"
may normalize to:
Alerts
But retain variants.
Do not accidentally merge genuinely different capabilities.
12. COMMON FEATURES
Identify:
features appearing across many relevant solutions
Example:
Analytics → 9/12User dashboard → 8/12Notifications → 7/12Search → 6/12
These are important because they are usually weak sources of differentiation.
13. RARE FEATURES
Identify:
features appearing in only a small number of solutions
But do NOT assume:
rare = innovative
A rare feature might simply be irrelevant.
Evaluate relevance separately.
14. FEATURE COMBINATION ANALYSIS
This is critical.
Innovation should not only ask:
“Does feature X exist?”
It should ask:
“Does the COMBINATION of features X + Y + Z already exist?”
Example:
Prediction+Offline mode
may individually exist.
But:
Prediction+offline mode+worker-assisted correction+automatic prioritization
may be uncommon.
Create:
interface FeatureCombination {  features: string[];  solutionIds: string[];  occurrenceCount: number;  noveltySignal:    | "common"    | "moderate"    | "uncommon";}
15. WORKFLOW LANDSCAPE
Features alone are not enough.
Compare complete workflows.
Create:
interface WorkflowLandscape {  commonWorkflowPatterns: WorkflowPattern[];  workflowGaps: WorkflowGap[];  underservedWorkflowStages: string[];}
16. WORKFLOW PATTERN
Example:
interface WorkflowPattern {  name: string;  steps: string[];  solutionIds: string[];  occurrenceCount: number;}
Example:
Input ↓AI prediction ↓Dashboard
appears across many systems.
This is a common workflow.
17. WORKFLOW GAP
Look for:
Input ↓existing process ↓existing output ↓missing step
Example:
Existing:detect→ classify→ reportMissing:automatic follow-up action
This is a potentially useful opportunity.
Create:
interface WorkflowGap {  description: string;  affectedSolutions: string[];  userImpact: string;  evidenceSourceIds: string[];  opportunityStrength: number;}
18. USER GAP ANALYSIS
Ask:
Which users are being ignored?Which users are underserved?Which users receive a poor workflow?Which context is poorly handled?
Example:
Most solutions:commercial kitchensProblem statement:college hostels
Potential gap:
student-hostel-specific workflow
Do not automatically call this novel; compare it with evidence.
19. CONSTRAINT GAP ANALYSIS
Look for constraints that existing solutions do not handle well:
offlinelow bandwidthlow budgetlow technical skilllimited hardwareprivacysmall organizationsstudent environments
Only use constraints that are relevant to the problem.
20. OPPORTUNITY AREA
Each detected opportunity should become:
interface OpportunityArea {  id: string;  title: string;  description: string;  basedOnGaps: string[];  affectedUsers: string[];  relevantExistingSolutions: string[];  potentialValue: string;  differentiationPotential: number;  feasibilityPotential: number;}
21. IDENTIFIED GAP
Create:
interface InnovationGap {  id: string;  type:    | "feature"    | "workflow"    | "user"    | "context"    | "constraint"    | "integration"    | "automation"    | "data"    | "other";  title: string;  description: string;  supportingSolutionIds: string[];  supportingSourceIds: string[];  impact: number;  confidence: number;}
22. GAP QUALITY RULE
A gap must have evidence.
Bad:
“Nobody provides WhatsApp integration.”
unless your research actually supports that conclusion.
Better:
“Among the researched solutions, none of the 12 direct solutions were found to expose a WhatsApp-based interaction workflow.”
This is much more defensible.
Use wording based on the research scope.
23. NEVER CLAIM ABSOLUTE NOVELTY
Never produce:
100% uniqueNobody has built thisFirst in the worldNo competitor exists
Instead use:
high differentiationmoderate differentiationlow differentiation
and describe the evidence.
24. CANDIDATE IDEA GENERATION
Generate approximately:
3–5 candidate solutions
Do not generate 20.
Each candidate must be grounded in an identified opportunity.
25. CANDIDATE IDEA SCHEMA
interface CandidateIdea {  id: string;  name: string;  oneLineDescription: string;  detailedDescription: string;  targetUsers: string[];  problemSolved: string;  keyFeatures: Feature[];  workflow: WorkflowStep[];  differentiators: Differentiator[];  opportunityIds: string[];  inspirationSources: string[];  potentialRisks: string[];  estimatedComplexity:    | "low"    | "medium"    | "high";  estimatedHackathonFit:    number;  innovationScore:    number;  impactScore:    number;  differentiationScore:    number;  overallConceptScore:    number;}
26. CANDIDATE GENERATION RULE
Every candidate must answer:
What existing gap does this address?Why is this different?Why would users care?Why can a hackathon team demonstrate it?
Do not generate generic:
"AI-powered platform"
ideas.
27. DIFFERENTIATOR
Create:
interface Differentiator {  statement: string;  differenceType:    | "feature"    | "workflow"    | "user"    | "context"    | "integration"    | "constraint"    | "automation"    | "combination";  comparedToSolutionIds: string[];  evidenceSourceIds: string[];  strength: number;}
Example:
Differentiator:"Automatically converts predicted demand into a preparation recommendation."Type:workflowCompared solutions:sol_1sol_4sol_7Strength:8.2
28. CANDIDATE EVALUATION
Evaluate each candidate using:
Problem FitUser ValueDifferentiationFeature NoveltyWorkflow NoveltyImpactHackathon FeasibilityDemo PotentialAI Necessity
Use 0–10 scores.
29. SCORE FORMULA
Use deterministic aggregation.
Example:
overallConceptScore =  problemFit * 0.15 +  differentiation * 0.20 +  featureNovelty * 0.15 +  workflowNovelty * 0.15 +  impact * 0.15 +  hackathonFit * 0.10 +  demoPotential * 0.05 +  aiNecessity * 0.05;
Keep weights configurable.
Do not let the LLM randomly invent the final score.
30. SELECTED IDEA
Select the highest-value candidate, but do not blindly choose the numerical winner.
Apply sanity checks:
Is the candidate actually relevant?Is its differentiation meaningful?Can a student team build an MVP?Is the idea understandable?Does it fit the hackathon?
If the mathematically highest candidate fails a hard requirement, choose the next valid candidate and explain why.
31. HARD REJECTION RULES
Reject a candidate if:
essentially identical to an existing solutionORrequires impossible resourcesORrequires unavailable data with no fallbackORcannot reasonably be demonstratedORviolates hackathon rulesORrequires prohibited technology
32. NOVELTY ASSESSMENT
Create:
interface NoveltyAssessment {  classification:    | "high_differentiation"    | "moderate_differentiation"    | "low_differentiation";  score: number;  reasoning: string;  strongestDifferentiators: string[];  majorOverlapAreas: string[];  closestExistingSolutions: string[];  evidenceSourceIds: string[];  confidence: number;}
33. NOVELTY SCORING
Novelty should consider:
feature overlapworkflow overlaptarget-user overlapproblem overlapfeature combination overlapdifferentiation strength
Example:
High overlap:problemusers3 core featuresLow overlap:workflowfeature combinationResult:moderate/high differentiation
34. IMPORTANT: NOVELTY ≠ FEATURE RARITY
Do NOT conclude:
Feature is rare→ therefore idea is novel
Instead:
Feature rarity+relevance+combination+workflow+user context
determine the differentiation signal.
35. CLOSEST EXISTING SOLUTION

top 3 closest solutions
and explain:
What overlaps?What differs?Why the difference matters?
Schema:
interface SolutionComparison {  solutionId: string;  overlap: string[];  differences: string[];  differentiationStrength: number;}

This keeps Innovation efficient while protecting against obvious false novelty.

60. INNOVATION AGENT EDGE CASE — NO CLEAR GAP
If existing solutions appear to cover the problem thoroughly:
Do NOT invent a fake gap.
Instead:
No strong obvious gap identified.
Then generate candidates from:
different user segmentdifferent contextbetter workflowbetter accessibilitybetter automationbetter constraint handling
If still weak:
selectedIdea = nullstatus = "insufficient differentiation"
Do not fabricate innovation.
The main graph should then decide whether to return to Researcher for additional investigation.
61. EDGE CASE — ONE EXISTING SOLUTION
If only one direct solution exists:
Do not claim novelty solely because there is only one.
Use:
direct solution:1adjacent:...research confidence:medium/low
and compare carefully.
62. EDGE CASE — MANY EXISTING SOLUTIONS
If there are 50+ existing solutions:
Use:
clustersfrequencyrepresentative solutions
instead of sending every full object into one giant LLM context.
Summarize systematically.
63. EDGE CASE — SIMILAR NAMES BUT DIFFERENT PRODUCTS
Do not merge merely because names are similar.
Use:
domainusersproblemfeaturesworkflow
to distinguish.
64. EDGE CASE — SIMILAR FEATURE WORDING
Normalize semantically, but preserve original evidence.
Example:
"Smart notifications""automated alerts"
may map to:
alerts
but store variants.
65. EDGE CASE — LLM SUGGESTS UNSUPPORTED GAP
If LLM claims:
“No competitor supports offline mode.”
but the ResearchResult contains an offline competitor:
reject that claim.
Gap analysis must be grounded in actual input data.
66. EDGE CASE — CANDIDATE IDENTICAL TO EXISTING SOLUTION
If:
candidate similarity > high threshold
reject candidate.
Generate another.
Do not present a copied idea as innovative.
67. EDGE CASE — CANDIDATE TOO COMPLEX
Example:
requires:IoTblockchaincomputer visiondronemobile app
Reject or simplify.
The Innovation Agent should prefer a strong MVP over feature overload.
68. EDGE CASE — AI IS UNNECESSARY
If the candidate can be solved entirely with:
CRUD+basic filtering
do not pretend AI is required.
Instead identify whether AI provides legitimate value.
69. AI NECESSITY
Candidate should explain:
Why AI is actually useful.
Examples:
unstructured data understandingpredictionclassificationsemantic matchingreasoningpersonalizationautomation
Not:
"because it's an AI hackathon."
70. HACKATHON FIT
Evaluate:
Can a working MVP be built?Can it be demonstrated?Can the team understand it?Can the value be shown quickly?

It does not redo unnecessary research.
It normalizes existing solutions.
It analyzes concrete features.
It calculates feature frequency programmatically.
It analyzes feature combinations.
It analyzes workflows.
It identifies meaningful evidence-backed gaps.
It distinguishes direct/adjacent/technical solutions.
It generates 3–5 candidates.

Candidate AI necessity is considered.

Closest existing solutions are identified.
Overlap and difference are explicitly explained.

Invalid output is retried.
Historical candidates are preserved.

Frontend can display the feature landscape.
Agent 4 can consume ProjectCapabilityRequirements.
