1. Agent 1 — Strategist
Tools needed: essentially none
I recommend keeping Agent 1 tool-free.
Problem Statement
       ↓
Gemini/Groq
       ↓
ProblemAnalysis
The Strategist is doing:
problem decomposition
user identification
pain-point identification
constraint extraction
terminology generation
research-question generation
These are reasoning tasks.
You don't need:
web search
GitHub
vector DB
at this stage.
Only optional utility
You can expose a hackathon_rules_parser if the hackathon rules are uploaded as a PDF/document, but even this can simply be a normal backend service rather than an agent tool.
So for Agent 1:
LLM
+
Zod validation
is enough.
2. Agent 2 — Researcher
This is where the majority of tools live.
The Researcher has two loops:
DISCOVERY
    ↓
ENRICHMENT
A. gemini_web_search
Purpose
Search the internet through Gemini's Google Search grounding.
Use it for:
products
startups
commercial solutions
hackathon projects
blogs
articles
research projects
general web discovery
Example:
"AI food waste management platform"
The tool should return:
{
  query,
  results: [
    {
      title,
      url,
      snippet,
      content?,
      citations?
    }
  ]
}
Why you need it
This gives you broad Google-backed discovery.
B. tavily_web_search
Purpose
Run the same logical query independently through Tavily.
Your architecture is:
Logical Query
    │
    ├── Gemini Search
    │
    └── Tavily Search
             ↓
         Merge Results
Example:
Query:
"AI food waste startup"
Run:
Gemini → results
Tavily → results
Then merge them.
Why two search providers?
Because they may discover different pages.
You want:
better recall
+
more diverse sources
+
less dependence on one provider
C. tavily_extract
Purpose
Sometimes search results only give you a snippet.
For an important candidate:
Search
 ↓
Candidate URL
 ↓
Tavily Extract
 ↓
Full useful page content
Use it primarily during enrichment, not discovery.
Example:
FoodWise website
Search found:
AI-powered food waste platform...
But you want:
features
workflow
target users
implementation details
So:
tavily_extract(url)
can retrieve deeper page content where available.
D. github_search_repositories
Purpose

Because GitHub API gives structured repository information and lets you perform repository-specific operations.

4. Agent 3 — Innovation
Agent 3 needs far fewer external tools because it is primarily a reasoning and analysis agent.
Its inputs are already:
ProblemAnalysis
+
ResearchResult
A. embed_text
Purpose
Generate vector representations for:
solutions
features
workflows
candidate ideas
Example:
"Forecast cafeteria meal demand"
and:
"Predict upcoming food consumption"
can be recognized as semantically similar.
You need embeddings for semantic comparison.
B. vector_search
Purpose
Find similar existing:
solutions
features
workflows
Example:
Candidate idea
      ↓
embedding
      ↓
vector search
      ↓
top 5 similar existing solutions
This is especially useful for detecting accidental similarity.
C. semantic_similarity
You can implement this as:
cosine similarity
using the embeddings.
This should be deterministic.
Use it for:
solution similarity
feature similarity
workflow similarity
candidate similarity
D. feature_normalizer
This can be a hybrid:
LLM
+
deterministic matching
Example:
"real-time alerts"
"instant notifications"
"threshold notifications"
→
Alerts
But preserve variants.
This is essential because otherwise feature frequency calculations become inaccurate.
E. feature_counter
Absolutely make this deterministic.
Given:
Solution A:
analytics, alerts, tracking
Solution B:
analytics, prediction
Solution C:
analytics, alerts
return:
analytics → 3
alerts → 2
tracking → 1
prediction → 1
Do not waste LLM calls doing arithmetic.
F. solution_clusterer
Can use:
embeddings
+
similarity
+
LLM naming
Example:
Solution embeddings
       ↓
clusters
       ↓
Cluster 1:
Demand Forecasting
Cluster 2:
Waste Tracking
Cluster 3:
Redistribution
The clustering algorithm can be deterministic; the LLM can explain/name clusters.
G. novelty_verification_search
This is an optional research tool for Innovation.
Normally:
Innovation
→ ResearchResult
→ analysis
But if the generated idea is suspiciously close to existing solutions:
candidate
 ↓
high similarity
 ↓
verification required
 ↓
Gemini + Tavily search
 ↓
new evidence
 ↓
re-evaluate
This is valuable because your Innovation Agent should not confidently select a concept that is obviously already implemented.

7. Which ones should ACTUALLY be LangChain tools?
This distinction is important.
Do not turn every function into a LangChain tool.
Genuine external-action tools
Make these LangChain tools:
gemini_web_search
tavily_web_search
tavily_extract
github_search_repositories
github_get_repository
github_get_readme
github_get_contents
Potentially:
novelty_verification_search
if exposed directly to the Innovation LLM.
Normal TypeScript services/functions
Keep these outside the LLM tool-calling interface:
source_normalizer
deduplicator
ranker
feature_counter
similarity_calculator
evidence_merger
coverage_checker
cache_service
This is cleaner and safer.

10. The most important thing for your architecture
Don't think:
26 tools = 26 agents
Think:
3 Agents
      │
      ├── 7 actual external tools
      │
      └── many deterministic internal functions
So your architecture stays clean:
                 HACKFORGE

The key principle for the later prompts
Tools should represent capabilities the LLM cannot directly perform. Functions should handle deterministic processing. Agents should handle reasoning and decisions.
That separation will keep your implementation much simpler, cheaper, and more reliable.
